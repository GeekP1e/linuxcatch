# LinuxCatch

Локальный тренажёр Linux: объяснение команды → упражнение в настоящем Bash → самостоятельная практика. 146 уроков и 16 практических задач, разделённых на 16 групп. Интерфейс, объяснения, задания, подсказки и сообщения проверки доступны на русском и английском; переключатель RU/EN сохраняет текущую сессию и прогресс. Арена пока не реализована.

Группы: навигация и пути; файлы и каталоги; параметры cp/mv/rm; ссылки; синтаксис Bash; текст и потоки; история и справка; Nano; Vim; SSH и почта; Bash и алиасы; процессы; пользователи и права; диски и разделы; файловые системы и монтирование; программный RAID. В каждой группе сначала обучение, затем задача без пошаговой инструкции.

## Запуск

Нужен Docker Engine с Compose на Linux или Docker Desktop в режиме Linux-контейнеров на Windows/macOS.

```bash
docker compose up --build -d --wait
```

Открой http://localhost:8080. Rust и Node.js на хосте для этого не нужны.

Для доступа с другого компьютера в локальной сети добавь в корневой `.env` настройки (замени `192.168.188.102` своим адресом):

```dotenv
FRONTEND_HOST=0.0.0.0
APP_ORIGINS=http://localhost:8080,http://127.0.0.1:8080,http://localhost:5173,http://127.0.0.1:5173,http://192.168.188.102:8080
```

Примени их через `docker compose up -d --wait`. Другой компьютер в той же сети открывает `http://192.168.188.102:8080`. При изменении адреса обнови `APP_ORIGINS`. Если соединение блокирует локальный firewall, разреши входящий TCP-порт 8080 для своей подсети.

На этой машине rootless Docker с pasta сбрасывает соединения с адресов, отличных от localhost. Поэтому в `.env` установлены `FRONTEND_HOST=127.0.0.1` и `FRONTEND_PORT=18081`, а TCP-прокси передаёт запросы с порта 8081 на `127.0.0.1:18081`. Он принимает подключения как по localhost, так и из локальной сети. Нужен установленный `socat`.

Прокси настроен в `~/.config/systemd/user/linuxcatch-lan.service` и включён для автоматического запуска при входе пользователя. Управление:

```bash
systemctl --user start linuxcatch-lan.service
systemctl --user stop linuxcatch-lan.service
```

На другом компьютере для этого варианта открывай `http://192.168.188.102:8081`; на этой машине также доступен `http://localhost:8081`. Прокси передаёт HTTP и WebSocket. В `APP_ORIGINS` добавлены `http://192.168.188.102:8081`, `http://localhost:8081` и `http://127.0.0.1:8081`. При изменении сетевого IP обнови `APP_ORIGINS` и перезапусти backend.

Linux, включая rootless Docker:

```bash
bash scripts/start.sh
```

Windows: запусти `start.cmd`. Пока скрипты запуска проверяют наличие Docker; автоматическая установка WSL/Docker и проверка в Windows-виртуалке — следующий этап.

Первый запуск скачивает базовые образы и собирает зависимости. Нужен интернет. Основной интерфейс и задания после сборки работают локально; используются локальные моноширинные шрифты.

Остановка:

```bash
docker compose down
```

При rootless Docker для прямого вызова Compose укажи путь к socket:

```bash
DOCKER_SOCKET=/run/user/$(id -u)/docker.sock docker compose up --build -d --wait
```

`scripts/start.sh` определяет путь автоматически с учётом приоритета `DOCKER_CONTEXT` над `DOCKER_HOST`. Для нестандартной конфигурации можно задать `DOCKER_SOCKET` явно. Удалённый Docker Engine в этом MVP не поддерживается; скрипт отклоняет такой endpoint до запуска Compose.

Переменная `RUST_BUILD_IMAGE` позволяет выбрать готовый образ для сборки backend. По умолчанию используется `rust:1.94-slim-bookworm`. На этой машине в игнорируемом `.env` настроены rootless socket и локальный образ с Rust 1.94 и кешем зависимостей: он использовался для проверки Compose при медленной загрузке базовых образов. Для переноса проекта используй значения по умолчанию.

## Структура

- `frontend/` — React, TypeScript, Vite, xterm.js; Nginx в контейнере раздаёт приложение и проксирует API/WebSocket.
- `backend/` — Rust, Axum, Tokio, Bollard. Docker API используется напрямую.
- `sandbox/` — Debian, Bash, coreutils, find, grep, sed, awk, man/info, Nano, Vim, less, OpenSSH, s-nail, procps, fdisk/cfdisk, parted, e2fsprogs, xfsprogs, sysstat, lsscsi, lsof, kmod, sudo и mdadm.
- `backend/content/course.json` — группы, тексты RU/EN, начальное состояние и проверки заданий. `setup`, `check` и тестовый `solution` не передаются клиенту.
- `backend/src/lessons.rs` — загрузка каталога и модели API.
- `frontend/src/i18n.ts` — переводы интерфейса; язык сохраняется в localStorage.

Каждый терминал получает отдельный контейнер. Терминальный ввод и вывод передаются по WebSocket, Bash работает через PTY. Поддерживаются `Tab`, история, пайпы, перенаправления, изменение размера и `Ctrl+C`.

Основные проверки учитывают состояние: каталоги, текущий путь, содержимое файлов, ссылки, права и временные метки. Для команд без сохраняемого результата (`clear`, `history`, `man`, `info`, `--help`) проверяется история Bash после возвращения к приглашению. Пройденные задания и текущий урок сохраняются в localStorage этого браузера; прогресс объединяется между вкладками одного адреса сайта. После повторного открытия восстанавливается урок, а терминал получает чистое окружение. Нажатие «Сбросить» создаёт чистое окружение, сохраняя прогресс.

SSH работает с настоящим сервером внутри той же учебной сессии: `ssh -p 2222 student@127.0.0.1`. Для него в образе подготовлены учебные ключи. Команда `mail` использует локальный транспорт: письмо записывается в `/workspace/outbox/message.eml`. Внешняя сеть и настоящая отправка писем для этих заданий не нужны.

## Администрирование и диски

Разметка через `fdisk`, `cfdisk` и `parted`, форматирование ext4, `tune2fs`, `blkid`, `fsck` и `xfs_repair` работают настоящими утилитами с обычными файлами-образами. Блочные устройства хоста не передаются контейнеру. Файлы-образы разреженные: логический размер может превышать фактически занятое место. Урок XFS получает 384 MiB памяти и tmpfs `/workspace` 192 MiB; обычные уроки сохраняют прежние лимиты.

Задания с `lab_model: true` в JSON используют **учебную модель** пользователей, sudo, монтирования и RAID. Интерфейс показывает пометку RU/EN. Команды модели находятся в `/opt/linuxcatch/lab/bin`; их данные и учебные `/etc/passwd`, `/etc/shadow`, `/etc/sudoers`, `/etc/fstab`, `mdadm.conf` — в `/workspace/lab`. Модель не меняет настоящие UID, пароли, таблицу монтирования или массивы ядра. Даже учебный root выполняется с настоящим UID 1000. Поддерживается полное учебное правило `NOPASSWD: ALL`; полноценный интерпретатор политик sudo не реализован. `sudo visudo` редактирует учебный файл настоящим visudo и проверяет синтаксис. Учебные пароли указаны в задании и не предназначены для реальных учётных записей.

Обычные уроки работают без этих подмен. `ps` видит PID-пространство контейнера; `uptime`, `iostat`, `lsblk` и `lsmod` могут отражать сведения общего ядра хоста. Уроки по LVM, tar, dump и gparted не добавлены: подтверждённых упражнений в предоставленном списке нет.

## Учебные сессии

- Максимум 4 одновременные сессии на сервер.
- На контейнер: 128 MiB памяти, 0.5 CPU, 64 процесса.
- Docker init убирает завершившиеся фоновые процессы, чтобы зомби не расходовали лимит процессов.
- Рабочая директория в tmpfs: 32 MiB; `/tmp` и `/home/student`: по 16 MiB.
- Непривилегированный пользователь, без capabilities и внешней сети; корневая файловая система доступна только для чтения.
- Сессия удаляется после закрытия соединения, 15 минут бездействия или 1 часа работы.
- Закрытие вкладки или остановка сервера отменяют подготовку окружения с удалением контейнера и освобождением слота. При остановке сервер ждёт завершения очистки сессий до 10 секунд, затем выполняет общую уборку.
- Проверка задания выполняется параллельно с терминалом; её лимит — 4 секунды. Зависшая проверка останавливается, после чего можно исправить файлы и повторить проверку в той же сессии.
- Ожидание заблокированного ввода, отправки данных или изменения размера терминала ограничено 5 секундами; такая сессия завершается с удалением контейнера.
- При остановке и следующем запуске сервер удаляет свои оставшиеся учебные контейнеры по метке `io.linuxcatch.sandbox=true`.

Это MVP для локального запуска: по умолчанию интерфейс опубликован только на `127.0.0.1`, аккаунтов и авторизации нет. Backend получает Docker socket и имеет права управлять Docker Engine. Socket не передаётся учебным контейнерам. Не публикуй эту конфигурацию в интернет без отдельной архитектуры доступа и изоляции. Запускай один экземпляр backend на один Docker Engine: очистка при запуске рассчитана на локальную установку.

## Разработка

Нужны Rust 1.94+, Node.js 20.19+ и Docker.

```bash
docker compose build sandbox
cd backend
cargo run
```

В другом терминале:

```bash
cd frontend
npm ci
npm run dev
```

Открой http://localhost:5173. Vite проксирует `/api` на `127.0.0.1:3000`. Backend учитывает `DOCKER_HOST`.

Если порт 3000 занят, запусти backend с `LISTEN_ADDR=127.0.0.1:3099`, а в `frontend/.env.local` укажи `LINUXCATCH_API_URL=http://127.0.0.1:3099`.

Переменные backend:

| Переменная | По умолчанию |
| --- | --- |
| `LISTEN_ADDR` | `127.0.0.1:3000` |
| `SANDBOX_IMAGE` | `linuxcatch-sandbox:local` |
| `APP_ORIGINS` | localhost/127.0.0.1 на портах 8080 и 5173 |
| `RUST_LOG` | задаётся Compose: `linuxcatch_backend=info` |

Для доступа с другого origin явно добавь его в `APP_ORIGINS`. Клиенты WebSocket обязаны отправлять разрешённый заголовок `Origin`.

## Проверки

```bash
cd frontend
npm run build
```

Все тесты находятся в корневой папке `tests/`.

```bash
cd backend
cargo fmt --check
cargo clippy --all-targets -- -D warnings
cargo test
```

С запущенным Compose:

```bash
cd backend
LINUXCATCH_TEST_URL=ws://localhost:8080 cargo test --test terminal -- --ignored --test-threads=1
```

Интеграционные проверки создают настоящие учебные контейнеры: проходят все 162 задания, проверяют незавершённое начальное состояние, альтернативные решения, сохранение в Nano/Vim через PTY, изоляцию сессий и отказ для постороннего origin. Дополнительно проверяются работа терминала во время зависшей проверки, остановка процесса проверки, повторная проверка, освобождение сессии при отключении и параллельное создание пользователей без потери записей. Последовательный запуск учитывает ограничение в четыре сессии.

Проверка отмены медленной подготовки окружения (из `backend/`):

```bash
cargo test --bin linuxcatch-backend session_tests -- --ignored --test-threads=1
```

Эти два теста обращаются к Docker напрямую и создают отдельные временные контейнеры и HTTP-сервер. При rootless Docker задай `DOCKER_HOST=unix:///run/user/$(id -u)/docker.sock` перед командой.

Из корня проекта:

```bash
bash tests/test-start.sh
bash tests/test-proxy.sh
```

Первая проверка подменяет Docker заглушкой и проверяет выбор socket без запуска контейнеров. Для второй нужны собранные образы frontend и sandbox: она создаёт отдельную сеть без опубликованных портов, меняет IP тестового backend и проверяет восстановление прокси с сохранением пути и query-параметров. Тестовые контейнеры и сеть удаляются при завершении.
